# BT-RB300 mwan3 boot race: r5 evaluation

This is a local test of an opt-in routing workaround, not a new MinScale
release. The tested router was a BT-RB300 (MT7981, OpenWrt 25.12.5, Linux
6.12.94) connected to Headscale. The r5 package retains the r4 LowMem feature
profile and adds one OpenWrt setting, `tailscale.settings.mwan3_compat=1`.

## Failure and change

Tailscale already selects policy-rule priorities 13xx when it detects active
OpenWrt `mwan3`. It checks while initializing the router. On this device,
`tailscaled` sometimes started before `mwan3` had installed its rules, selected
52xx instead, and then lost Tailnet and DNS routing when `mwan3` installed rule
2001. Restarting `tailscaled` after `mwan3` was ready selected 13xx and restored
connectivity. Tailscale issue
[#12667](https://github.com/tailscale/tailscale/issues/12667) already describes
this boot ordering failure; we are not claiming it as a newly discovered bug.

The [r5 source recipe](../../profiles/bt-rb300-r5/README.md) adds an opt-in
`MINSCALE_FORCE_MWAN3=1` path to Tailscale's existing 13xx rule setup. The
OpenWrt init script sets that environment variable only when the UCI option is
enabled. Its default is off, so normal startup keeps upstream detection.
No permanent address-specific or Tailnet-prefix rules are added to OpenWrt.

## Exact artifact and device result

The signed local evaluation APK was
`tailscale-lowmem-1.103.0_pre20260924-r5-compact-aarch64_cortex-a53.apk`,
9,914,657 bytes, SHA-256
`5a97a8ac062c1f1addd8a8b743645379c20aebf32928be0b749c9fe7f052954a`.
The installed `tailscaled` SHA-256 was
`155780c67f2fc55d9bff9c50403cb383e6750a15bce8db2ecfbb46e698b0b49c`.
The profile patch, inputs, and packaging scripts are in the recipe; executable
and package files are kept outside Git.

After upgrading r4 to r5 and enabling the UCI option, a real router reboot
started the same daemon with the expected procd environment. Both IPv4 and
IPv6 had rules 1310, 1330, 1350, and 1370. IPv4 `mwan3` rule 2001 was also
present; no temporary 110x routing exceptions were installed. The daemon log
confirmed the configured 13xx selection.

| Post-boot check | Result |
| --- | --- |
| Headscale connection, direct peer, TSMP | Pass |
| MagicDNS UDP4, TCP4, UDP6, TCP6 | Pass; actual queries over each transport |
| TCP4 receive / transmit | 304.0 / 382.7 Mbit/s |
| TCP6 receive / transmit | 298.5 / 365.1 Mbit/s |
| Four-stream TCP4 receive / transmit | 280.2 / 368.0 Mbit/s |
| UDP4 receive / transmit | 20.0 / 20.0 Mbit/s, 0% loss in the short test |
| Recovery after traffic | One daemon PID throughout the 120-second sample; no metrics gaps |

During the final minute of that recovery sample, median RSS was 24.98 MiB:
7.89 MiB anonymous and 17.09 MiB file-backed. Heap allocation was about
2.9 MiB and the daemon had 68 goroutines. Peak RSS in the two-minute sample
was 25.61 MiB. No OOM kill or panic appeared in the current kernel log.

The prior r4 build completed a separate two-hour soak, but r5 has **not**
completed one. This result establishes a targeted cold-boot fix on this router,
not general `mwan3` compatibility. WAN failover, exit-node use, subnet routing,
endpoint roaming, and other firmware versions need separate checks before r5
can replace the published r4 candidate. The r5 package remains a local
evaluation build.
